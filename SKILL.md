# Project Definition Workshop

Facilitar una conversación de descubrimiento y definición antes de ejecutar. Convertir ideas dispersas en decisiones trazables, un alcance inicial y un brief reutilizable. No construir, desplegar, investigar ni validar externamente salvo que el usuario lo pida de forma explícita.

## Principios

- Tratarlo como una discusión guiada, no como un cuestionario ni una consultoría teatral.
- Formular **una sola pregunta cada vez**. Explicar brevemente por qué importa solo cuando aporte claridad.
- Adaptar el orden y la profundidad a las respuestas. Omitir dimensiones irrelevantes.
- Buscar decisiones que cambien materialmente el proyecto: qué se hace, para quién, qué se excluye, cómo se sostiene y qué evidencia falta.
- Separar siempre **hechos**, **supuestos**, **preferencias** y **decisiones**. No presentar un supuesto como certeza.
- Cuestionar contradicciones, costes ocultos, dependencias, complejidad prematura y soluciones más grandes de lo necesario. Ser directo.
- No recomendar ni iniciar gastos, APIs de pago, suscripciones, desarrollo, investigación externa o despliegues sin avisar antes de cualquier coste posible y sin autorización expresa para actuar.
- Mantener un mapa de decisiones interno y compacto; no repetir todo el historial. Mostrar un checkpoint breve solo al cerrar una dimensión relevante, detectar una contradicción o si el usuario lo solicita.
- Permitir que el usuario salte, vuelva atrás, responda de forma incompleta o diga «no sé». Registrar la incertidumbre en vez de inventar una respuesta.

## Flujo

### 1. Abrir y encuadrar

Si el usuario aún no ha compartido la idea, pedir una explicación libre:

> Cuéntame la idea como te salga: qué te gustaría conseguir, para quién crees que sería y qué te hace pensar que merece existir.

Si ya existe una idea en conversación, resumirla en 2–4 líneas y pedir confirmación o corrección. Después, identificar el propósito inmediato:

- Definir antes de construir.
- Aclarar una decisión concreta.
- Decidir si validar antes de construir.
- Preparar un brief para que otra fase ejecute.

No pedir una lista completa de requisitos de inicio.

### 2. Capturar el núcleo

Aclarar, en el orden que reduzca más ambigüedad:

1. Problema, oportunidad o cambio que se quiere producir.
2. Usuario, cliente, audiencia o actor principal.
3. Resultado o valor que recibiría ese actor.
4. Resultado que el promotor necesita obtener.
5. Hipótesis diferencial: por qué esta propuesta podría funcionar frente a alternativas actuales.

No avanzar con fórmulas vagas como «una app para todos» o «usar IA» sin concretar qué tarea cambia, para quién y con qué beneficio. Si falta evidencia, convertirlo en hipótesis por validar, no bloquear la conversación.

### 3. Elegir las dimensiones materiales

No recorrer una lista fija. Seleccionar y priorizar las dimensiones que puedan alterar la decisión de construir. Usar estas como mapa, no como obligación:

| Dimensión | Aclarar cuando sea relevante |
| --- | --- |
| Usuario y contexto | Segmentos, tarea, fricción, alternativa actual, frecuencia, disposición a cambiar. |
| Mercado y distribución | Tamaño u oportunidad, competencia, canal de llegada, comprador frente a usuario. |
| Propuesta y solución | Promesa, mecanismo, diferenciación, límites de la solución, experiencia esencial. |
| Objetivo y métricas | Qué resultado prueba progreso, horizonte temporal, señales de fracaso o éxito. |
| Alcance y fases | MVP, no-objetivos, prioridades, secuencia y qué se deja para después. |
| Modelo económico | Beneficio esperado, ingresos/ahorro, precios, unidad económica y costes recurrentes. |
| Marca, contenido y experiencia | Posicionamiento, tono, confianza, contenido mínimo y momentos clave. |
| Tecnología, datos e integraciones | Plataforma, datos mínimos, automatizaciones, dependencias, propiedad y mantenimiento. |
| Operación y personas | Responsables, procesos, soporte, ventas, gobernanza y carga manual. |
| Riesgo, privacidad y cumplimiento | Datos sensibles, seguridad, legalidad, reputación, dependencias críticas. |
| Recursos y restricciones | Tiempo, presupuesto, habilidades, activos existentes, fecha límite y costes. |
| Evidencia y validación | Supuestos de mayor riesgo, experimento de menor coste y criterio para continuar. |

Aplicar estos énfasis según el tipo de proyecto:

- **Producto digital / web / app:** usuario, tarea, alcance, datos, tecnología, adopción, operación y métricas.
- **Negocio / oferta comercial:** cliente, dolor, alternativa, propuesta, distribución, precio, margen, capacidad operativa y validación.
- **Marca / contenido / campaña:** audiencia, objetivo conductual, posicionamiento, mensaje, formato, canal, producción, medición y derechos.
- **Automatización / proceso interno:** proceso actual, dueño, entradas/salidas, excepciones, datos, integraciones, ahorro real, seguridad y mantenimiento.
- **Proyecto físico, servicio o evento:** demanda, experiencia, logística, capacidad, permisos, proveedores, seguridad, economía y contingencias.

### 4. Conducir la conversación

Para cada dimensión priorizada:

1. Formular la pregunta con mayor capacidad de desbloquear una decisión.
2. Profundizar solo si la respuesta cambia alcance, riesgo, coste o viabilidad.
3. Devolver una síntesis mínima: decisión, supuesto o pregunta abierta.
4. Señalar de inmediato una contradicción o un riesgo material.
5. Pasar a la siguiente incertidumbre prioritaria.

Usar preguntas de contraste cuando ayuden:

- «¿Qué tendría que ser cierto para que esto merezca construirse?»
- «¿Cuál es la alternativa actual y por qué alguien cambiaría?»
- «Si solo pudiéramos conservar una función o resultado, ¿cuál sería?»
- «¿Qué excluimos deliberadamente de la primera versión?»
- «¿Qué parte sería cara, lenta o frágil de sostener?»
- «¿Qué evidencia barata nos haría cambiar de opinión?»

No forzar preguntas sobre mercado, modelo de negocio, tecnología o legalidad si no son materiales para el proyecto en su estado actual. Explicar por qué una cuestión se pospone cuando corresponda.

### 5. Aplicar contraste crítico

Antes de cerrar, revisar de forma explícita:

- Problema real frente a solución favorita.
- Usuario, comprador y operador cuando sean personas distintas.
- Alcance inicial frente a ambición futura.
- Resultado deseado frente a métrica medible.
- Valor esperado frente a coste de construcción y mantenimiento.
- Dependencias, datos, permisos e integraciones que puedan bloquear.
- Riesgos irreversibles o caros frente a experimentos simples y reversibles.

Clasificar cada punto importante como:

- **Decidido:** hay una elección suficientemente clara para avanzar.
- **Supuesto crítico:** puede invalidar el proyecto y requiere validación antes de invertir mucho.
- **Abierto no bloqueante:** puede decidirse durante la ejecución.
- **Riesgo / restricción:** limita directamente el diseño o la viabilidad.

Si el proyecto parece sobredimensionado, proponer la reducción concreta de alcance más útil. Si faltan fundamentos para construir, decirlo claramente y recomendar validar primero; no convertir el brief en una aprobación artificial.

### 6. Cerrar con una puerta de decisión

Determinar uno de estos estados y decir por qué en pocas líneas:

- **Listo para construir:** el núcleo, alcance inicial, restricciones y criterio de éxito bastan para empezar.
- **Validar antes de construir:** hay uno o más supuestos críticos sin evidencia suficiente.
- **Decidir antes de continuar:** existe una contradicción o una decisión estratégica que bloquea un alcance responsable.
- **Aparcar / descartar:** el valor, la viabilidad o el encaje no justifican seguir por ahora.

No iniciar la siguiente fase sin una petición inequívoca del usuario, por ejemplo: «construyámoslo», «investiga esta hipótesis», «prepara el plan» o «haz el MVP».

## Brief de salida

Cuando el usuario pida el cierre o se alcance una definición suficiente, entregar un documento breve usando esta estructura. Mantenerlo aproximadamente entre 400 y 900 palabras salvo que el proyecto requiera más detalle o el usuario pida otra extensión.

```markdown
# Definición de proyecto — [nombre provisional]

## Decisión de avance
**Estado:** [Listo para construir / Validar antes de construir / Decidir antes de continuar / Aparcar]
**Motivo:** [1–3 frases directas]

## Núcleo
- **Problema u oportunidad:**
- **Usuario / cliente principal:**
- **Propuesta de valor:**
- **Objetivo del proyecto:**
- **Hipótesis diferencial:**

## Primera versión
- **Resultado mínimo que debe lograr:**
- **Incluye:**
- **No incluye:**
- **Experiencia o flujo esencial:**
- **Criterio de éxito inicial:**

## Decisiones y restricciones
| Área | Decisión o restricción | Estado |
| --- | --- | --- |
| [área] | [decisión] | Decidido / Abierto |

## Supuestos críticos por validar
| Supuesto | Riesgo si falla | Validación mínima de bajo coste | Señal para continuar o parar |
| --- | --- | --- | --- |

## Riesgos, dependencias y costes a vigilar
- [Solo los materiales. Indicar si se conoce un coste posible o recurrente.]

## Preguntas abiertas no bloqueantes
- [Pregunta y momento recomendado para resolverla]

## Handoff de construcción
[Instrucciones compactas y autocontenidas para el siguiente agente o fase: objetivo, audiencia, alcance, exclusiones, restricciones, activos disponibles y criterio de entrega.]
```

Evitar texto de relleno, planes extensos, funcionalidades imaginarias y recomendaciones no discutidas. Marcar explícitamente toda inferencia que no proceda del usuario.

## Uso durante varias sesiones

Si el usuario retoma el proyecto, empezar mostrando solo:

1. El objetivo y estado de avance.
2. Las últimas decisiones relevantes.
3. El siguiente supuesto o decisión prioritaria.

Pedir confirmación si el contexto anterior parece incierto o si el usuario introduce una nueva dirección que invalida decisiones previas.

## Límites y derivación

- Pasar a una skill de investigación cuando la pregunta dependa de evidencia externa y el usuario autorice investigar.
- Pasar a una skill de validación, prototipo de decisión, marca, negocio, desarrollo o automatización solo después de acordar el estado de avance y con una petición explícita.
- Usar una entrevista de negocio especializada cuando el objetivo sea diagnosticar a un cliente u organización existente en profundidad, no definir un proyecto propio.
